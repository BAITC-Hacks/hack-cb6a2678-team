# ML-сервис

> **Актуально:** ML-сервис уже есть (`ML/`, см. `ML/README.md`). Контракт с бэкендом — `contracts/ml-service.openapi.yaml` v2.0
> (`POST /v1/forecast`), текущие задачи — [ml-tasks.md](ml-tasks.md), план стыковки — [ml-integration.md](ml-integration.md).
> Раздел «Что сдать» и упоминания `/predict` ниже — первоначальный план, оставлен как справка о требованиях к данным.

Задача: модель, которая по почасовому **прогнозу погоды** предсказывает **нормализованную мощность** турбины (0..1)
на 24–48 ч вперёд, с интервалом неопределённости P10/P50/P90. Отдаётся как Python-сервис (FastAPI),
который вызывает бэкенд.

## Что сдать

```
ml/
├─ README.md            — как обучить и запустить
├─ requirements.txt     — зафиксированные версии
├─ Dockerfile           — сервис на порту 8000
├─ train.py             — обучение воспроизводимо одной командой, фиксированный seed
├─ app.py               — FastAPI: /health, /predict
├─ features.py          — признаки; ОДИН код для обучения и /predict
└─ models/              — обученные файлы модели (коммитятся — жюри не будет обучать сами)
```

Контракт — `contracts/ml-service.openapi.yaml`. Если нужны другие поля погоды — сначала поменяйте контракт
и скажите бэкенду: погоду из Open-Meteo достаёт бэкенд.

## Данные

- **Факт**: исторические данные станции (март 2023 — 31.01.2026): время, средний ветер м/с,
  нормализованная активная мощность, температура °C. Две турбины.
- **Погода для обучения**: архивные *прогнозы* погоды за тот же период по координатам турбин.
  Обучать на прогнозах, а не на фактическом ветре станции: в бою модель будет видеть только прогноз,
  и его ошибки она должна «выучить».

  В бою (backtest февраля) используется ECMWF IFS HRES 9 км (`ecmwf_ifs`) из Open-Meteo Single Runs API.
  **Его архив прогонов начинается 14.03.2024** — для 2023 года таких данных нет. Варианты:

  | Период | Источник | Замечание |
  |---|---|---|
  | 14.03.2024 – 31.01.2026 | Single Runs API, `ecmwf_ifs`, те же прогоны, что и в бою | лучший вариант: обучение и инференс на одном источнике |
  | 01.2024 – 03.2024 | Previous Runs API (`..._previous_day1`) | прогноз с заблаговременностью ~24 ч |
  | 03.2023 – 12.2023 | Historical Forecast API | склейка первых часов прогонов — почти факт, оптимистично; лучше не использовать или только для экспериментов |

  Скорее всего, ~22 месяцев (с 14.03.2024) хватит. Выгрузку делаем через бэкенд (`WeatherService`, тот же кэш),
  формат часа — `WeatherHour` из контракта. Договоритесь с бэкендом о формате выгрузки (CSV/Parquet).
  Узел сетки модели — ~5 км от турбин, одинаковый для обеих.
- Координаты: t1 — 43.645150, 78.535604; t2 — 43.643198, 78.538828.

Первым делом выясните **часовой пояс** «статистического времени» (UTC или UTC+5) и приведите всё к UTC.

## Жёсткие требования

1. **Обучение только на данных ≤ 2026-01-31 23:00 UTC.** Февраль 2026 — тест, его нельзя видеть ни в обучении,
   ни при подборе гиперпараметров. Валидацию делайте на последних месяцах до февраля (например, декабрь–январь).
2. **Никаких признаков из будущего.** В `/predict` приходит только прогноз погоды — не используйте факт мощности
   или факт ветра за прогнозируемые часы. Лаги факта (мощность «сейчас») допустимы только на момент `forecastIssuedAt` и раньше.
3. Выход: `0 ≤ p10 ≤ p50 ≤ p90 ≤ 1` для каждого часа, в том же порядке, что и вход.
4. Воспроизводимость: фиксированный seed, зафиксированные версии библиотек.

## Идеи для признаков

- Ветер на высоте ступицы: интерполяция между 80/100/120 м или степенной закон от 10 м.
- Куб скорости ветра (мощность ∝ v³ до номинала).
- Плотность воздуха по температуре и давлению (зимой при −25 °C воздух плотнее — мощность выше при том же ветре).
- Направление ветра (sin/cos), порывы.
- Час суток, заблаговременность (часов от `weatherIssuedAt`).
- Риск обледенения: температура около 0 °C + высокая влажность.

## Очистка истории

Выкиньте из обучения часы, где мощность явно не отражает погоду: ветер нормальный, а мощность ≈ 0 долго
(простой, ремонт), или мощность «срезана» на постоянном уровне (ограничение диспетчером). Иначе модель выучит простои.

## Модель

Любая на ваш выбор. Практичный вариант — LightGBM с `objective="quantile"` (три модели: alpha 0.1/0.5/0.9)
или CatBoost с `MultiQuantile`. Отдельная модель на турбину или общая с признаком `turbineId`.

## Метрики, которые мы покажем жюри

- MAE / RMSE по часам 1–24 и по заблаговременности 1–48.
- Сравнение с бейзлайнами: persistence и «кривая мощности по сырому прогнозу ветра».
- Покрытие интервала [P10, P90] — должно быть около 80 %.

Сообщите бэкенду версию модели (`modelVersion`, например `lgbm-v1`) — она показывается в интерфейсе.
