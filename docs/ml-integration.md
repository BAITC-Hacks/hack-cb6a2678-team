# План стыковки ML ↔ бэкенд

Состояние на 23.09.2026, после коммита ML `5f16e0b`. Всё ниже проверено запуском, а не только чтением кода.

## Что есть в ML

- FastAPI-сервис `ML/windml/api.py`, порт 8000:
  - `POST /v1/forecast` `{site: turbine_1|turbine_2, issue_date, weather_source: previous_runs|live}` → 48 часов;
  - `GET /v1/models`, `GET /v1/models/{site}` — есть ли модель и её метаданные;
  - `GET /tools`, `POST /tools/{name}` — инструменты для LLM (`run_backtest`, `train_model` и др.).
- Модель: LightGBM (среднее + P10/P50/P90) поверх эмпирической кривой мощности. Вход — ансамбль прогнозов
  ECMWF IFS 0.25 + GFS + ICON из Open-Meteo **Previous Runs API**, режим `strict`.
- Погоду ML достаёт **сам** из своего кэша `ML/data/cache/`. Кэш покрывает 12.2023–02.2026: весь февраль отвечает
  без сети, ~30 мс на запрос.
- Тесты: 20 проходят (после двух исправлений окружения, см. «Что поправить в ML»).
- Качество на январе 2026 (модели обучены по 31.12.2025): nMAE ≈ 20 % против ≈ 30 % у бейзлайна «постоянная
  средняя». Модель **завышает** выработку в среднем на ~9.8 п.п., интервал P10–P90 покрывает 68–70 % вместо 80 %.

Пример ответа (`issue_date=2026-01-31`):

```json
{ "site": "turbine_1", "issue_date": "2026-01-31",
  "target_start": "2026-02-01 00:00:00", "target_end": "2026-02-02 23:00:00",
  "weather_source": "open-meteo-previous-runs", "weather_hash": "4fee95592457d6f5",
  "analysis": { "status": "warning", "recommended_action": "accept_and_recheck_on_update",
                "issues": [ {"code": "HIGH_NWP_DISAGREEMENT", ...}, {"code": "WIDE_INTERVAL", ...} ],
                "stats": { "mean_power": 0.366, "peak_hour": "...", "hours_below_5pct": 0, ... } },
  "hourly": [ {"time": "2026-02-01 00:00:00", "lead_day": 1, "forecast": 0.098, "p10": 0.007, "p50": 0.010, "p90": 0.183}, ... ] }
```

## Главные расхождения с бэкендом

| | Бэкенд сейчас (API v1.1) | ML | Решение |
|---|---|---|---|
| Кто достаёт погоду | бэкенд передаёт погоду в `/predict` | ML сам, по `issue_date` | **Принимаем схему ML.** Модель обучена на ансамбле трёх моделей из Previous Runs; пересобирать её вход на бэкенде — риск рассинхрона признаков |
| Эндпоинт | `POST /predict` | `POST /v1/forecast` | берём `/v1/forecast`; `contracts/ml-service.openapi.yaml` переписываем под реальный API |
| Момент прогноза | 00:00 UTC даты, горизонт 24/48 ч | день D, 12:00 местного, цель — сутки D+1 и D+2 | **Переходим на схему ML**: она буквально совпадает с ТЗ («на 31 января — прогноз на следующие 24–48 ч») |
| Время в ответе | UTC (`Instant`) | местное, без зоны (`"2026-02-01 00:00:00"`) | ML отдаёт ISO со смещением; бэкенд переводит в UTC |
| Ревизии | 4 в день (00/06/12/18 UTC) | нет: Previous Runs даёт одно значение на сутки заблаговременности | см. «Ревизии» ниже |
| Погода по часам в ответе | `windSpeed`, `temperature` в каждой точке | не возвращается | попросить ML добавить (данные у него уже есть) |
| Время выпуска погоды | `weatherIssuedAt` | неявно (`previous_day2/3`) | попросить ML вернуть явную границу |
| Метрики за февраль | считаем по факту | факта за февраль нет ни у кого | метрики — на январском тесте ML |

## Решения

### Момент прогноза и бэктест

- Выпуск: день **D, 12:00 местного** (07:00 UTC при UTC+5). Цель: сутки D+1 и D+2, 48 часов.
- Даты выпуска в бэктесте: **2026-01-31 … 2026-02-26** (27 выпусков × 2 турбины = 54 вызова ML).
  Выпуск 26.02 покрывает 27–28.02. Выпуск 27.02 выходит за февраль и требует мартовской погоды, которой нет в кэше.
- `horizonHours=24` → сутки D+1, `48` → D+1 и D+2.

### Ревизии

Внутридневных ревизий у ML нет, и честно сделать их на Previous Runs нельзя. Предлагаю переосмыслить ревизию
как **повторный расчёт одних и тех же суток по более свежей погоде**. Это прямо требование ТЗ
«повторный расчёт при обновлении входных данных»:

- сутки X прогнозируются дважды: в выпуске X−2 (как D+2) и в выпуске X−1 (как D+1, по более свежему прогнозу погоды);
- `GET /api/forecast/revisions` для суток X возвращает обе версии и изменение между ними;
- агент в цикле сравнивает новую версию с предыдущей (`compareWithPrevious`) и пишет, что изменилось.

`revisionsPerDay` в `/api/meta` становится 1, параметр `revision` у `/api/forecast` уходит.

### Погода: два источника с разными ролями

- **Вход модели** — погода ML (Previous Runs, ансамбль). Её использует только ML.
- **Клиент погоды бэкенда** (`backend/.../weather/`, Single Runs, `ecmwf_ifs`) остаётся для агента:
  чат о погоде, алерты «обледенение» и «шторм», пояснения в отчёте. На вход модели он не идёт.
- Оба источника соблюдают защиту от утечки. В README честно описываем, зачем их два.

### Что агент берёт от ML, а что нет

- Бэкенд вызывает только `POST /v1/forecast` и `GET /v1/models`.
- `/tools` ML **не отдаём LLM**: там `train_model` и `run_backtest`, которые агенту в бою вызывать нельзя,
  и это дублировало бы нашего агента. Агент один — в `backend/`.
- `analysis` из ответа ML — готовые выводы, это ровно то, что нужно маленькой LLM. Маппинг:

| ML `analysis.issues[].code` | Наш `alerts[].type` |
|---|---|
| `HIGH_NWP_DISAGREEMENT` | `low_confidence` (warning) |
| `WIDE_INTERVAL` | `low_confidence` (info) |
| `ML_VS_PHYSICS_GAP` | новый тип `model_physics_gap` (warning) |
| — (из клиента погоды бэкенда) | `icing`, `storm_cutout` |
| — (правила бэкенда по точкам) | `ramp_up`, `ramp_down` |

- `predictedPower` = `forecast` (среднее; у него меньше MAE, чем у `p50`), полоса — `p10`–`p90`.
  Проверено: `forecast` во всех 48 часах лежит внутри [p10, p90].
- `summary` считаем на бэкенде по точкам, как сейчас: одинаково для всех источников.

### Метрики

Факта за февраль нет (датасет кончается 31.01.2026). Экран «Качество» и `/api/metrics` строим по
**январскому тесту ML** (`ML/outputs/training/<site>/test_predictions.csv`):

- модели для теста обучены по 31.12.2025, январь в обучении не участвовал — метрики честные;
- в CSV есть `actual`, `forecast`, `p10`/`p90`, `lead_day`, `pc_baseline` (кривая мощности без ML → наш
  `powerCurveBaselineMae`), `anomaly` (простои);
- persistence-бейзлайн (`baselineMae`) бэкенд считает сам по SCADA из датасета;
- `byLeadTime` — по `lead_day` (1 и 2), а не по 48 часам. Либо по часам 1–48 от момента выпуска — это даёт ту же ось.

В `/api/meta` добавляем `metricsFrom=2026-01-01`, `metricsTo=2026-01-31`. Для февральских прогнозов
`actualPower = null`.

## Изменения публичного API (v1.2)

- `/api/meta`: `backtestFrom=2026-01-31`, `backtestTo=2026-02-26`, `revisionsPerDay=1`, `issueTimeLocal="12:00"`,
  `metricsFrom`, `metricsTo`.
- `/api/forecast`: убрать `revision`; точки — часы суток D+1(/D+2) в UTC; `forecastIssuedAt` = D 12:00 местного в UTC.
- `/api/forecast/revisions`: версии прогноза **для целевых суток** (из выпусков X−2 и X−1).
- `alerts[].type`: добавить `model_physics_gap`.
- `/api/metrics`: период по умолчанию — январь 2026.
- Фронтенду: ограничить выбор даты `backtestFrom..backtestTo`, убрать переключатель 00/06/12/18.

## Тонкости для бэкенда

- `hourly[].time_utc` у ML — **начало** часа, к которому относится значение (среднее SCADA за час).
  В публичном API бэкенда `ForecastPoint.timestamp` описан как **конец** часового интервала.
  При маппинге: `timestamp = time_utc + 1 ч`, либо поменять описание в публичном API на «начало часа» — решить один раз и везде одинаково.
  Погода бэкенда (Open-Meteo) — мгновенные значения на метку времени.
- Поля «v2» до выхода новой версии ML отсутствуют: клиент бэкенда читает их как `null`. Для перехода
  `time_utc` можно вычислить из `time` и `Asia/Almaty`.

## Что поправить в ML (задачи ML-щику)

Полное задание для ML-щика (для Claude Code) — [ml-tasks.md](ml-tasks.md). Кратко:

| # | Проблема | Почему важно | Что сделать |
|---|---|---|---|
| 1 | **Часовой пояс.** `LOCAL_TZ="Asia/Almaty"` даёт UTC+6 до 01.03.2024 и UTC+5 после. Корреляция ветра станции с ERA5 по 10-минутным данным лучшая при **UTC+6 и до, и после** 01.03.2024 (t1: 0.787 при +6 против 0.764 при +5 после марта; у t2 то же) | Почти всё обучение (с 01.2024) сдвинуто на 1 час относительно погоды | Попробовать фиксированный UTC+6 (`Etc/GMT-6`) и сравнить ошибку на январском тесте. Спросить организаторов |
| 2 | Сохранённые модели требуют `pyarrow`, его нет в `requirements.txt` | На чистой машине модель не загрузится | Добавить `pyarrow` |
| 3 | LightGBM на macOS требует `libomp` | Жюри на Mac без Docker не запустит | Dockerfile (`python:3.12-slim` + `libgomp1`); в README — `brew install libomp` |
| 4 | `hourly[].time` без часового пояса | Бэкенд должен угадывать зону | Отдавать ISO со смещением (или добавить `time_utc`) |
| 5 | В ответе нет погоды по часам | Точки API требуют `windSpeed`, `temperature` | Добавить в `hourly` средний по ансамблю ветер на 100 м и температуру |
| 6 | Нет явной границы выпуска погоды | Нужна для `weatherIssuedAt` и доказательства честности | Добавить `weather_issued_before` (UTC): самый поздний момент выпуска использованных прогнозов |
| 7 | Каждый прогноз со статусом `warning` (`HIGH_NWP_DISAGREEMENT` + `WIDE_INTERVAL` везде) | Предупреждение, которое горит всегда, ничего не значит | Пересмотреть пороги (например, по перцентилям на обучении) |
| 8 | Завышение ~9.8 п.п. и покрытие интервала 68–70 % | Прямо бьёт по метрикам | Калибровка смещения на валидации; расширение интервала (conformal) до ~80 % |
| 9 | `SITES` содержит только turbine_1; для turbine_2 взята погода turbine_1 | Допущение висит в ответе API | Добавить turbine_2 (43.643198, 78.538828). Турбины в 300 м друг от друга, в одной ячейке сетки — погода, вероятно, та же, но это стоит зафиксировать |
| 10 | Датасет лежит в корне `ML/` с дублированным именем, `data/raw/` пустая, а команда обучения ссылается на `data/raw/turbine_1.csv` | Воспроизводимость | Переложить в `ML/data/raw/turbine_1.csv`, `turbine_2.csv` |

| 2 | бэкенд | ✅ `contracts/ml-service.openapi.yaml` v2.0 под `/v1/forecast` |

| 4 | бэкенд | Контракт API v1.2 и моки под новую семантику времени (раздел выше), сообщить фронту |
| 5 | бэкенд | Цикл агента: `predict` (ML) → `validate` → алерты (ML `analysis` + погода бэкенда) → отчёт LLM → сохранение |
| 6 | бэкенд | Бэктест: 27 выпусков × 2 турбины → `data/backtest/*.json` (коммитится), API читает из хранилища, моки уходят |
| 7 | бэкенд | Метрики из `test_predictions.csv` + persistence по SCADA |
| 8 | ML | Пункты 1, 7, 8 (пояс, пороги, калибровка) → переобучение. Бэкенд просто перезапускает бэктест |
