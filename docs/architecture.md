# Архитектура

## Компоненты

```
                       ┌──────────────────────────┐
  Браузер ───────────► │ frontend (React)          │  4 экрана: прогноз, шаги агента, качество, чат
                       └────────────┬─────────────┘
                                    │ REST /api/** (openapi.yaml)
                       ┌────────────▼─────────────┐
                       │ backend (Spring + Kotlin) │
                       │  ├─ REST API              │
                       │  ├─ агент (Spring AI)  ───┼──► ollama (qwen3:8b) — «мозг» агента
                       │  ├─ клиент погоды      ───┼──► Open-Meteo (архивные прогнозы погоды)
                       │  ├─ хранилище прогнозов   │
                       │  └─ backtest-раннер       │
                       └────────────┬─────────────┘
                                    │ POST /predict (contracts/ml-service.openapi.yaml)
                       ┌────────────▼─────────────┐
                       │ ml (Python FastAPI)       │  модель «погода → мощность», P10/P50/P90
                       └──────────────────────────┘
```

Всё поднимается через `docker compose up --build` (см. README).

| Компонент | Технологии |
|---|---|
| frontend | React 19, TypeScript, Vite, Recharts, Leaflet; в Docker — nginx с прокси `/api` |
| backend | Spring Boot 4.1, Kotlin 2.3, Spring AI 2.0.1, springdoc |
| ollama | Ollama, `qwen3:8b` |
| ml | Python, FastAPI, LightGBM (среднее + квантили), изотоническая кривая мощности |

## Цикл агента

`backend/.../cycle/ForecastCycleService.kt`, запуск — `POST /api/forecast/run`, журнал — `GET /api/agent-log`.
Для турбины и дня выпуска D (момент прогноза — D 12:00 местного):

```
1. fetchWeather          Open-Meteo Single Runs: прогон, опубликованный ≤ момента прогноза; недоступен → более старый
2. predict               ML /v1/forecast → 48 ч P10/P50/P90; сбой → повтор (шаг retrying), после 2 повторов цикл failed
3. validate              48 ч подряд, мощность 0..1, p10 ≤ прогноз ≤ p90, погода не из будущего; не прошёл → прогноз отклонён
4. compareWithPrevious   сутки D+1 этого выпуска = сутки D+2 вчерашнего: изменение средней мощности, «существенное» ≥ 5 п.п.
5. llm                   отчёт для диспетчера по готовым выводам; самопроверка: все времена и проценты из текста
                         должны быть в данных, иначе отчёт отклоняется и берётся шаблон (так же без Ollama)
6. saveForecast          прогноз + журнал → data/cycles/<турбина>/<дата>.json (коммитится)
```

Порядок шагов фиксирован, чтобы прогноз получался всегда; решения внутри шагов принимаются по данным и
каждое видно в журнале. Отчёт цикла подставляется в `GET /api/forecast`.

## Роль LLM и роль ML — не путать

- **ML-модель** считает числа (мощность по погоде). Детерминированно, воспроизводимо.
- **LLM-агент** — оркестратор: решает, какие инструменты вызвать, проверяет результат, объясняет его человеку.
  LLM **никогда** не выдумывает и не считает числа сама — только пересказывает то, что вернули инструменты.

Агент реализован на Spring AI: инструменты — методы Kotlin с аннотацией `@Tool` (`backend/.../agent/AgentTools.kt`),
цикл «LLM → вызов инструмента → результат → LLM» крутит `ChatClient`. Каждый вызов инструмента пишется в журнал
(`toolCalls` в ответе чата; в будущем — `agent-log` цикла прогноза).

## Защита от утечки данных из будущего

Это главное требование ТЗ и главная ловушка.

- Используются **прогнозы** погоды, а не фактическая погода или reanalysis.
- Прогноз погоды берётся только из прогона, **опубликованного** до момента `T`. Источник — Open-Meteo Single Runs API,
  который отдаёт конкретный прогон по времени инициализации (`run=`). Прогон считается опубликованным через
  `weather.publication-delay` = 7 ч после инициализации (Open-Meteo: «обычно 4–6 ч для глобальных моделей», берём с запасом).
  Поэтому в 00:00 UTC используется прогон 12 UTC предыдущего дня. Правило одно на весь код:
  `WeatherService.latestAvailableRun(T)`.
- Момент `T` передаётся во все инструменты агента кодом, а не LLM — модель не может его подменить.
- Каждый прогноз хранит `weatherIssuedAt` (≤ `forecastIssuedAt`), шаг получения погоды в журнале — `dataIssuedAt`.
  Фронт показывает это как «✓ данные не из будущего».
- ML-модель обучается только на данных ≤ 2026-01-31 23:00 UTC.
- Факт (`actualPower`) используется только для метрик и отображения, никогда — как вход модели для того же периода.

## Источник погоды

| | |
|---|---|
| API | Open-Meteo Single Runs API, `https://single-runs-api.open-meteo.com/v1/forecast?...&models=ecmwf_ifs&run=YYYY-MM-DDTHH:00` |
| Модель | ECMWF IFS HRES 9 км (`ecmwf_ifs`) — единственная модель с архивом прогонов на февраль 2026 (архив с 14.03.2024; остальные модели — только с 02.04.2026) |
| Прогоны | 00/06/12/18 UTC; 00 и 12 — на 7 суток, 06 и 18 — на ~6 суток |
| Переменные | ветер 10/80/100/120 м, направление 100 м, порывы 10 м, температура 2 м, влажность 2 м, давление у поверхности |
| Сетка | обе турбины попадают в один узел ~9 км (43.620, 78.479, высота 555 м), в ~5 км от турбин |
| Кэш | сырые ответы в `data/weather-cache/<model>/<lat>_<lon>/<run>.json`, коммитятся в репозиторий |
| Отказ | прогон недоступен или неполный → берётся предыдущий (до 2 шагов назад), пропуски в `skippedRuns` |

## Выпуск прогноза и версии

- Выпуск — день D, 12:00 местного (Asia/Almaty, UTC+5); цель — сутки D+1 и D+2 местного времени, 48 часов.
  Даты выпуска в backtest: 31.01–26.02.2026.
- Вход ML — Open-Meteo Previous Runs в режиме `strict`: для суток D+k берётся прогноз, сделанный за k+1 суток до часа,
  поэтому самый поздний использованный прогноз выпущен не позже (D−1) 23:00 местного.
- **Версии прогноза:** каждые сутки X прогнозируются дважды — из выпуска X−2 (как D+2) и из выпуска X−1 (как D+1,
  по более свежей погоде). Это «повторный расчёт при обновлении входных данных»: шаг цикла `compareWithPrevious`
  и `GET /api/forecast/revisions`. Внутридневных версий нет — архив Previous Runs хранит прогнозы с шагом в сутки.

## Метрики

Факта за февраль нет, поэтому метрики — на отложенном тесте (январь 2026) тестовой модели ML, обученной по 31.12.2025
(`GET /v1/evaluation` у ML):

- `mae`, `rmse`, `mape`, `bias` — по суткам D+1.
- `baselineMae` — persistence: факт за последний полный час перед выпуском (11:00–12:00 местного) на всё окно.
- `powerCurveBaselineMae` — кривая мощности по прогнозу ветра, без ML. Показывает вклад модели.
- `intervalCoverage` — доля часов, где факт попал в [P10, P90]; хорошо калиброванный интервал ≈ 0.8.
- `byLeadTime` — MAE по часам окна 1–48.

## Принятые решения и почему

| Решение | Почему |
|---|---|
| Локальная LLM (Ollama), а не API NVIDIA/OpenAI | Выданные на хакатоне ключи нельзя коммитить, а жюри должно запускать без них |
| `qwen3:8b`, `think: false` | Нормально вызывает инструменты, влезает в ноутбук; «размышления» сильно замедляют на CPU |
| ML — отдельный Python-сервис, а не ONNX внутри Spring | Признаки считаются одним кодом при обучении и инференсе; нет риска рассинхрона Python ↔ Kotlin |
| Признаки считает ML-сервис, бэкенд шлёт «сырую» погоду | Та же причина; бэкенд не знает деталей модели |
| Квантили P10/P50/P90 | Диспетчеру важен диапазон, а не одна цифра; есть критерий «ценность» |
| Готовая `summary` в ответе | LLM плохо считает; фронту тоже удобнее |
| Версии прогноза на сутки из двух выпусков | Требование ТЗ «повторный расчёт при обновлении входных данных»; чаще архив погоды не позволяет |
| Самопроверка отчёта LLM | Малая модель изредка выдумывает времена и проценты; отчёт с ними отклоняется |
| Агенту — только готовые выводы в местном времени | Модель плохо считает и подписывала UTC-метки как местные |
| Статический `openapi.yaml` как источник правды | Фронт и бэкенд договариваются о контракте до реализации |
| Результаты backtest коммитятся в репозиторий (`data/cycles/`) | Жюри видит всё сразу, даже без LLM и сети |
| Все времена UTC | Исключить ошибки со сдвигом на 5 ч между прогнозом и фактом |
