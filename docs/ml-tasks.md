# Задание для ML-части (для Claude Code / Codex)

> **Как использовать.** Откройте Claude Code в корне репозитория и напишите:
> «Выполни задание из docs/ml-tasks.md. Сначала часть A целиком, потом часть B. После каждой задачи запускай тесты».
> Ассистент сам прочитает `AGENTS.md` с общими правилами проекта.

## Контекст

Ты работаешь в папке `ML/` — Python-пакет `windml`: FastAPI-сервис прогноза выработки ВЭС (2 турбины)
на сутки D+1 и D+2 от выпуска в день D в 12:00 местного времени. Модель — LightGBM (среднее + P10/P50/P90)
поверх эмпирической кривой мощности. Вход — ансамбль архивных прогнозов погоды ECMWF/GFS/ICON из Open-Meteo
Previous Runs API (режим `strict`). Подробности — `ML/README.md`, `ML/TRAINING.md`.

Сервис вызывает бэкенд (`backend/`, Spring Boot + Kotlin, там же LLM-агент). **Контракт между ними —
`contracts/ml-service.openapi.yaml` (v2.0). Это источник правды:** твоя задача — довести сервис до него.
Поля, помеченные в контракте «v2», сейчас отсутствуют — их нужно добавить.

Почему всё это важно: жюри хакатона оценивает соответствие ТЗ, честность (нет утечки данных из будущего)
и воспроизводимость (проект должен запускаться у них одной командой). ТЗ — `docs/task.md`.

## Правила (нарушать нельзя)

1. **Никаких данных из будущего.** Февраль 2026 — период прогноза, факта за него нет и быть не должно.
   Обучение рабочих моделей — только по 2026-01-31 включительно. Погода — только прогнозы, выпущенные до момента выпуска.
2. **Январь 2026 — отложенный тест.** На нём только *измеряем* итоговое качество. Любой выбор (часовой пояс,
   гиперпараметры, калибровка, пороги) делай на валидации **до** января (например, ноябрь–декабрь 2025),
   с моделью, обученной строго до начала валидации. Иначе январские метрики станут нечестными.
3. **Не менять запрос `/v1/forecast`** (`site`, `issue_date`, `weather_source`) и семантику выпуска
   (D 12:00 местного → сутки D+1 и D+2). Ответ можно только расширять, существующие поля не удалять и не переименовывать.
4. **Не трогать** `backend/`, `frontend/`, `contracts/`, `docs/` (кроме `ML/*.md`). Если контракт кажется неудобным
   или ошибочным — не меняй его, а опиши проблему в итоговом отчёте.
5. Все существующие тесты должны проходить. На каждую задачу — новый тест.
6. Всё, что нужно для запуска (модели, кэш погоды, данные), лежит в репозитории: жюри не будет ничего качать и обучать.

## Часть A — интеграция (без переобучения; блокирует бэкенд, делать первой)

### A1. Зависимости и запуск

- Сохранённые модели при загрузке требуют `pyarrow`, а его нет в `requirements.txt` → на чистой машине
  модель не загружается. Добавь `pyarrow`. Зафиксируй версии всех зависимостей (`==`), с которыми проходят тесты.
- Добавь `ML/Dockerfile` (`python:3.12-slim` + `libgomp1` для LightGBM) и `ML/.dockerignore`.
  Сервис: `uvicorn windml.api:app --host 0.0.0.0 --port 8000`. Healthcheck — `GET /health`.
- В `ML/README.md` — запуск без Docker; отметь, что на macOS LightGBM требует `brew install libomp`.

**Готово, когда:** `docker build -t windml ML && docker run -p 8000:8000 windml` отвечает на `POST /v1/forecast`
для `issue_date=2026-01-31` **без сети** (`--network none`), из кэша в образе.

### A2. Время в UTC

Сейчас `hourly[].time`, `target_start`, `target_end` — местное время без зоны; бэкенду приходится угадывать.
Добавь (старые поля оставь):

- `issued_at_utc` — D 12:00 местного в UTC (`...Z`);
- `local_tz` — пояс, в котором заданы D 12:00 и сутки D+1/D+2;
- `target_start_utc`, `target_end_utc`;
- `hourly[].time_utc` — начало часа, к которому относится значение.

**Готово, когда:** для `issue_date=2026-01-31` при `local_tz=Asia/Almaty` (UTC+5 в 2026)
`issued_at_utc = 2026-01-31T07:00:00Z`, `hourly[0].time_utc = 2026-01-31T19:00:00Z`, 48 часов подряд без пропусков и дублей.

### A3. Доказательство честности и версия модели

- `weather_issued_before_utc` — самый поздний возможный момент выпуска использованных прогнозов погоды,
  **вычисленный консервативно** из `previous_dayN` и времени каждого часа. Должно выполняться
  `weather_issued_before_utc ≤ issued_at_utc`; если нет — сервис обязан отказать (503), а не отдать прогноз.
- `leakage_mode` (`strict`/`standard`), `weather_models` (список моделей ансамбля).
- `model_version` — стабильный идентификатор рабочей модели (например, `lgbm-<дата обучения>`), также в `GET /v1/models/{site}`
  вместе с `trained_until_utc`, `local_tz`, `weather_models`.

**Готово, когда:** тест проходит все выпуски 2026-01-31…2026-02-26 для обеих турбин и проверяет
`weather_issued_before_utc ≤ issued_at_utc`.

### A4. Погода по часам в ответе

В `hourly[]` добавь `wind_speed_100m` (среднее по ансамблю, м/с), `wind_spread` (СКО между моделями, м/с),
`temperature_2m` (среднее по ансамблю, °C). Эти данные уже есть внутри `predict` — их нужно только вернуть.

### A5. Интервалы в `analysis.issues`

Для проблем, привязанных ко времени (например, `HIGH_NWP_DISAGREEMENT` — часы с большим разбросом),
добавь `from_utc` и `to_utc` (последний час включительно). Если часов несколько отдельных групп — отдельная issue на группу.

### A6. Отложенный тест по HTTP

Добавь `GET /v1/evaluation/{site}` по контракту: строки из `outputs/training/<site>/test_predictions.csv`
с `time_utc`, `issue_date`, `lead_day`, `forecast`, `p10`, `p50`, `p90`, `actual`, `pc_baseline`, `anomaly`,
`wind_speed_100m`; плюс `model_version` и `trained_until_utc` **тестовой** модели и границы периода.
Бэкенд считает по ним метрики для экрана «Качество».

### A7. Данные на своих местах

Датасет лежит в корне `ML/` с задвоенным именем, `ML/data/raw/` пустая, а команды обучения ссылаются на
`data/raw/turbine_1.csv`. Переложи в `ML/data/raw/turbine_1.csv` и `turbine_2.csv`, убери дубли, проверь,
что команды из `TRAINING.md` работают как написано.

### A8. Тест на соответствие контракту

Тест, который загружает `contracts/ml-service.openapi.yaml` и проверяет ответы `/v1/forecast`,
`/v1/models/{site}`, `/v1/evaluation/{site}` на соответствие схемам (обязательные поля, типы, enum,
`0 ≤ p10 ≤ p50 ≤ p90 ≤ 1`, `p10 ≤ forecast ≤ p90`, ровно 48 часов). Например, через `jsonschema`
по `components/schemas` или `openapi-core`.

**Итог части A:** все тесты зелёные, Docker-образ работает без сети, ответ соответствует контракту v2.0.

## Часть B — качество модели (с переобучением)

Порядок важен: B1 меняет обучающие данные, поэтому идёт первым. После части B — переобучить тестовые
(по 2025-12-31) и рабочие (по 2026-01-31) модели обеих турбин и обновить `outputs/` и таблицу в `TRAINING.md`.

### B1. Часовой пояс SCADA

`config.LOCAL_TZ = "Asia/Almaty"` означает UTC+6 до 01.03.2024 и UTC+5 после. Но анализ бэкенда показывает,
что **время SCADA, вероятно, осталось на UTC+6 и после 01.03.2024**. Корреляция 10-минутного ветра станции
с ERA5 на 100 м (Open-Meteo archive):

| Сдвиг | t1 до 01.03.2024 | t1 после | t2 до | t2 после |
|---|---|---|---|---|
| UTC+5 | 0.734 | 0.764 | 0.737 | 0.759 |
| UTC+5:30 | 0.757 | 0.783 | 0.759 | 0.778 |
| **UTC+6** | **0.764** | **0.787** | **0.766** | **0.782** |
| UTC+6:30 | 0.756 | 0.778 | 0.759 | 0.773 |

Сделай:

- Разведи два понятия: **пояс SCADA** (для перевода обучающих данных в UTC) и **операционный пояс**
  (в нём задаются D 12:00 и сутки D+1/D+2; это официальное время Казахстана, `Asia/Almaty`, UTC+5 в 2026).
- Для пояса SCADA сравни `Asia/Almaty` (текущий), фиксированный `Etc/GMT-6` (UTC+6) и `Etc/GMT-5` (UTC+5)
  **по ошибке на валидации до января** (правило 2). Выбери лучший, запиши сравнение в `TRAINING.md`.
- Проверь сам: воспроизведи корреляцию с ERA5 (`https://archive-api.open-meteo.com/v1/archive`) или сдвигом
  относительно прогнозов из кэша.

### B2. Систематическое завышение

На январском тесте модель завышает выработку в среднем на ~9.8 п.п. Найди причину (например, простои,
которые исключены из обучения, но есть в оценке; сезонность; сдвиг пояса из B1 — проверь после B1).
Если после B1 смещение осталось — калибровка, подобранная **на валидации**, не на январе.

### B3. Калибровка интервала

P10–P90 накрывает 68–70 % факта вместо 80 %. Откалибруй на валидации (например, conformal-расширение
по заблаговременности). **Цель:** покрытие на январском тесте 75–85 %.

### B4. Осмысленный `analysis.status`

Сейчас `warning` у каждого прогноза (`HIGH_NWP_DISAGREEMENT` и `WIDE_INTERVAL` срабатывают всегда) — такое
предупреждение ничего не сообщает. Подбери пороги по распределению на обучении (например, 80-й и 95-й перцентили)
так, чтобы на выпусках февраля `warning` был примерно у 20–35 %, а `critical` — редкость.
Добавь в `TRAINING.md` таблицу: код → порог → доля срабатываний.

### B5. Турбина 2

`SITES` содержит только `turbine_1`; для `turbine_2` взята погода первой (`weather_site_assumption`).
Координаты турбины 2 из ТЗ — **43.643198, 78.538828** (в ~300 м от первой). Добавь её в `SITES`.
Проверь, отличается ли погода Previous Runs для этих координат (скорее всего, та же ячейка сетки).
Если отличается — докачай кэш и переобучи `turbine_2` на своей погоде. Если нет — зафиксируй это
в `TRAINING.md` и убери допущение из ответа (`weather_site_assumption: null`).
